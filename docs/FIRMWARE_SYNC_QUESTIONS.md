# 固件 / APP 接口确认单（v1.8）

用途：APP 侧已按 `../HTTPAPI/V821CAM-HTTP-API.md` **v1.8** 实现。下面每一条都是
「文档没写死 / 有两种合理读法」的地方。请固件侧逐条确认；若与我们当前假设不同，
右侧写了 APP 需要改什么，避免只改一边。

> 每条的「验证方式」都可以直接在设备上跑，用数据回答，不用讨论。

---

## 1. `GET /list` 的返回顺序（最关键）

**我们的假设**：`/list` 按**最老在前**（升序）返回；文档示例的顺序也是升序
（14:30 在 15:05 之前）。

**为什么在意**：分页是 `offset/limit`。如果顺序是升序，`offset=0` 拿到的是最老的
20 张——旧版 APP 就是这么翻页的，导致相册首页显示最老的照片。

**APP 当前做法**：不依赖服务端方向。首次打开用 `limit=2` 探一次（比较首尾文件名），
把「用户视角的 offset（跳过最新 N 张）」翻译成服务端 offset；两种顺序都能正确工作。

**请确认**：
- [ ] 升序（最老在前）
- [ ] 降序（最新在前）
- [ ] 有顺序参数（例如 `?sort=`），请给出参数名与取值

**验证方式**：

```bash
curl -s "http://192.168.5.1/list?offset=0&limit=4" | python3 -m json.tool
```

看 `files[].name` 是递增还是递减。

## 2. `total` 的时效性

**我们的假设**：`total` 是当前 DCIM 文件总数，任意 `offset/limit` 都会返回。

**为什么在意**：升序时我们用 `total` 反推「最新一页」的服务端 offset
（`serverOffset = total - offset - limit`）。如果 `total` 只在特定条件下返回、
或会把视频/子目录算不同，反推就会错位。

**请确认**：
- [ ] `total` 每次请求都返回，含义稳定
- [ ] `total` 只统计当前目录的 `IMG_*` / `VID_*`
- [ ] `limit` 上限确实是 50（超出会被截断而不是报错）

**验证方式**：

```bash
curl -s "http://192.168.5.1/list?offset=0&limit=1" | python3 -m json.tool
curl -s "http://192.168.5.1/list?offset=0&limit=200" | python3 -m json.tool   # 看是否 400 或截断
```

## 3. `mtime` 回填的范围

**我们的假设**：`/rtc` 回填「本次开机产生」的文件 mtime；不回填关机前拍的、
也不回填别的设备插卡带进来的照片。

**为什么在意**：APP 把 `mtime` 写进导出文件的 mtime 与 EXIF `DateTimeOriginal`。
如果回填范围变了（例如把整个 DCIM 都平移），已经导出的历史照片时间会与相机端不一致。

**请确认**：
- [ ] 只回填本次开机产生（文件名时间 ≥ 开机时钟）
- [ ] 每次开机只回填一次（首次 `/rtc`）
- [ ] `mtime_fixed` 是本次实际平移的文件数

**验证方式**：断电重启 → 不连 APP 先拍两张 → 连 APP（触发 `/rtc`）→ 看响应里的
`delta` 与 `mtime_fixed`，再对比 `/list` 的 `mtime` 是否变成真实时间。

## 4. 文件名与时钟的关系（保证顺序的前提）

**文档写的是**：「开机恢复的时间不会早于磁盘上最新一张，所以文件名字典序 = 拍摄先后」。

**为什么要固件确认**：APP 现在**完全依赖**这条来排序（不用 `mtime`）。如果某次开机
恢复的时间比最新文件早（哪怕 1 秒），新拍的照片文件名就会排到旧照片前面，
顺序就乱了。

**请确认**：
- [ ] 开机播种时钟时，取 `max(.last_time, 最新文件时间)`，保证单调
- [ ] 关机期间不存在「时间倒退」路径（例如未校时的 `hwclock` 读写）

**验证方式**：拍几张 → 断电几小时 → 再拍一张 → 看新文件名是否大于旧文件名。

## 5. `clock_synced` 的语义与时机

**我们的假设**：
- `false` = 本次开机尚未被 APP/token 自愈校时 → APP 必须在发任何 token 请求前 `POST /rtc`；
- 成功 `/rtc` 后立刻变 `true`（下一次 `/info` 就能读到）。

**为什么在意**：APP 在宣布「已连接」之前会 `await` 一次 `/rtc`。如果 `clock_synced`
永远返回 `false`（例如只在内存里翻标志、但 `/info` 读另一个变量），每次连接都会多一次
无谓的 3 秒等待。

**请确认**：
- [ ] `/rtc` 成功 → 紧接着 `GET /info` 的 `clock_synced` 为 `true`
- [ ] 重启后回到 `false`
- [ ] token 自愈成功也会把它置为 `true`

**验证方式**：

```bash
curl -s "http://192.168.5.1/info" | python3 -m json.tool        # 看 clock_synced
curl -s -X POST -H "Content-Type: application/json" \
     -d "{\"timestamp\":$(date +%s)}" "http://192.168.5.1/rtc"  # 触发校时
curl -s "http://192.168.5.1/info" | python3 -m json.tool        # 应为 true
```

## 6. `boot_id` 的生成规则

**我们的假设**：每次开机一个新值，同一开机期间不变；格式随意（UUID 即可）。

**为什么在意**：APP 用它判断「设备重启过 → 丢弃旧的时钟偏移并重新校时」。

**请确认**：
- [ ] 每次开机变化
- [ ] 同一次开机内稳定（不会因为 `/rtc`、休眠等改变）
- [ ] 有 `boot_id` 的接口：`/info`、`/list`、`/rtc` 三处一致

---

## 7. `hwclock_ok=false` 是否真的无害

**我们的假设**：`false` 只表示没有 RTC 供电，写入失败属正常，`/rtc` 仍然算成功
（`status=ok`）。APP 不当失败处理、不重试。

**请确认**：
- [ ] `/rtc` 的 HTTP 状态码与 `status` 字段只反映「系统时钟是否设置成功」
- [ ] `hwclock_ok=false` 时 `status` 仍为 `"ok"`

## 8. 缩略图与列表的耦合（性能）

**现状**：APP 拿到列表后，对每一张并发请求 `/thumb/<name>`。首屏 20 张 ≈ 20 个
并发请求（APP 侧有并发上限）。

**想确认**：固件端并发处理这么多 `/thumb` 是否会拖慢或掉连接？

- [ ] 20 并发无压力
- [ ] 建议 APP 侧降低并发（给出建议值）
- [ ] 最好提供列表内嵌缩略图（可选字段），APP 可省一轮请求

> 这一条不影响正确性，只影响相册打开速度。
